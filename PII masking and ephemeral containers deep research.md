# Mask requirement text first, containerize sandbox only

req2qa should pursue both initiatives, but on sharply different timelines and in a specific order: ship a **PII-masking pass over requirement text at test-generation time first**, and treat **full ephemeral-container-per-test execution as a large, deferred migration** — with a much smaller, immediately buildable version (containerizing only the Playwright/browser sandbox) as the actual next step for isolation. This ordering is forced by req2qa's real architecture, not a preference: the app runs as a **single EC2 instance, one systemd-managed uvicorn process**, with `JobRegistry` cancellation implemented as a plain in-process `threading.Event` and `ai_client.py`'s `_RequestGate` enforcing an account-wide **~10 requests/minute Bedrock quota** as a process-local gate. An internal architecture review (council code review, 2026-09-27) flagged both of these as hard blockers to full container-per-test execution: each container would spin up its own `_RequestGate` instance and silently blow past the tuned account-wide RPM quota, and `cancel_event` cannot cross a container/process boundary without a redesign. Masking, by contrast, has no such blocker — it is a local, synchronous text transform that fits cleanly into `qa_engine.py`'s existing five call sites with no architectural rework, provided it is scoped narrowly (only requirement-text inputs, fail-open on error, and explicitly not touching live page-snapshot text) to avoid a distinct new risk: masking a real success message before the LLM sees it could turn a genuine PASS into a false BLOCKED verdict.

## The rate gate and cancel-event are the real blockers, not compute cost or latency

req2qa's docstrings already say, in plain language, that today's design assumes exactly one process. `JobRegistry`'s own comments state it is "deliberately in-memory-only" and that multiple workers would "need this registry... revisited first," while `ai_client.py`'s `_RequestGate` docstring states the gate "is per PROCESS" and that running N worker processes would require dividing the RPM budget N ways or exceeding the account's Bedrock quota. This is exactly the internal review's finding: container-per-test execution multiplies the number of processes making Bedrock calls, and each one enforcing its own local ~10 RPM gate does not divide the quota — it multiplies effective throughput past the ceiling the team spent significant tuning effort establishing. Cancellation has the identical shape: `_RequestGate.acquire`'s `GateCancelled` path only works because `cancel_event` is a `threading.Event` shared in-process between the HTTP-triggered background task and the gate, and Playwright's own official Docker documentation confirms there is no built-in mechanism for cross-container cancellation signaling — that has to be built by the application, typically as a polled shared flag, since ephemeral workers have no long-lived socket back to the API process ([Playwright official docs: Docker](https://playwright.dev/docs/docker)). The lowest-friction fix for cancellation across a real boundary is polling a shared store (Redis key, DynamoDB item, or a relocated `exec_status` row) at the same 0.5-1s cadence `_RequestGate.acquire` already uses — reusing an existing polling rhythm rather than inventing a push-based signal that ephemeral compute cannot receive.

Compute-platform choice is a secondary question that only matters once those two blockers are addressed, and the notes are unambiguous about which platform wins on pure duration fit: **Lambda's hard 15-minute execution ceiling is a poor match** for req2qa's agentic loop, where `MAX_AGENT_STEPS=60` plus per-step Bedrock calls queued behind the shared RPM gate means a single test case can legitimately run for several minutes with no hard upper bound today ([BrowserCat: Running Playwright on AWS Lambda](https://www.browsercat.com/post/running-playwright-on-aws-lambda-challenges-solutions)). Lambda also carries a confirmed, apparently-unresolved production bug: the standard `@sparticuz/chromium` layer leaks roughly 25-30MB of `/tmp` debris per invocation despite `browser.close()` being called, filling a 1GB `/tmp` after 30-40 invocations and causing `ERR_INSUFFICIENT_RESOURCES` failures — with the original reporter stating "I wish i knew of one" fix even after trying 4GB and 8GB ephemeral storage ([Sparticuz/chromium GitHub Issue #231](https://github.com/Sparticuz/chromium/issues/231)). Fargate removes the hard timeout ("no limitations on running time" — [Artillery: Introducing full AWS Fargate + Playwright support](https://www.artillery.io/blog/introducing-fargate-playwright-browser-load-testing)) but costs **30-45+ seconds of task-provisioning latency per run**, and AWS's own guidance for exactly this pattern recommends either migrating short jobs back to Lambda or keeping a persistent pool of task consumers rather than launching a fresh task per request ([AWS re:Post: How to speed up provisioning of ECS Fargate task](https://repost.aws/questions/QUjZAzJd27SZWxXM7MgyxOZw/how-to-speed-up-provisioning-of-ecs-fargate-task)). Docker-on-EC2 starts fastest (sub-second to low single-digit seconds for a pre-pulled image) but provides no real infrastructure isolation — containers on the same host still share one kernel, one network namespace pool, and one point of compromise; what they actually buy is credential and artifact hygiene between concurrent test runs, not a hardened security boundary.

## The full migration is a four-part project, not a container swap

The internal review's second point — that this is a large lift, not an incremental one — is corroborated in detail by the architectural notes. Moving execution fully out-of-process requires solving four independent problems simultaneously before a single ephemeral worker can run a live test case reliably: **(1)** replacing `JobRegistry`'s threading-based cancellation with a shared, polled store; **(2)** porting `_RequestGate`'s comparatively sophisticated fairness logic — interactive-vs-background priority, per-access-code round robin, `GateCancelled` for queued requests — onto a centralized backend such as a Redis token bucket, since an off-the-shelf rate limiter will not replicate that business logic out of the box; **(3)** migrating every artifact write (screenshots, run logs, `exec_status` files) from local disk to S3 or equivalent shared object storage, and updating every read path including the client-facing status page and the final report builder; and **(4)**, if Lambda is chosen, engineering around the unresolved `/tmp`-accumulation bug before trusting it at real volume. Each of these is independently non-trivial, which is why the notes tier this "large" rather than "medium" effort. Compounding this, no source found addresses porting a priority-plus-round-robin fairness gate to a distributed backing store — that specific piece is original architectural inference, not a cited pattern — and no source benchmarks Redis-Lua token buckets at a ceiling as tight as **8-10 RPM account-wide**, where clock skew and Redis round-trip latency between workers become proportionally more dangerous than they would be at typical API-gateway RPM scales, since a single miscounted request can trip Bedrock's 429 (source: council review; corroborating gap noted in `ephemeral_containers.md`).

Docker-on-EC2 is the comparatively cheap path specifically because host and containers can still share local disk and a Docker socket: artifacts can stay on a shared bind-mount (no S3 migration needed), and cancellation can use `docker stop`/`kill` issued by the orchestrating process instead of a distributed flag — options Lambda and Fargate simply don't have. That leaves only the AI-fairness-gate problem to solve for real, and even there, a same-host IPC mechanism (a Unix-socket-based gate broker) is a materially smaller lift than a full Redis-backed distributed limiter, since the gate never has to leave the host. This is precisely why the internal review's recommended first step is not "adopt Docker-on-EC2 for full test execution" but something narrower still.

## Smallest-safe-first-step: sandbox only, proxy AI calls through the existing gate

The reviewer's recommended first slice threads the isolation goal through the rate-gate blocker rather than around it: **containerize only the Playwright/browser sandbox portion of each test** — for clean per-test teardown and credential/artifact hygiene — **while proxying AI calls back through the existing single in-process rate gate**, rather than containerizing the whole loop including AI calls. This captures the actual value Docker-on-EC2 was shown to offer (a crashed or compromised test-case container can't read another run's screenshots or in-memory secrets) without touching `_RequestGate` or `cancel_event` at all, since the process making Bedrock calls never leaves the host. It is a genuinely incremental step: it requires a per-test container image with Playwright plus `execute_engine.py`'s sandbox logic, a bind-mounted artifact volume, and a thin proxy/IPC path back to the existing gate — not a distributed rate limiter, not S3, not a rewrite of cancellation. Full container-per-test execution (AI calls included) should stay off the roadmap until the fairness-gate and cancellation redesigns are separately funded as their own project, because attempting it prematurely is exactly the failure mode the internal review flagged: silently exceeding a quota the team already spent significant effort tuning.

## Masking belongs at generation time, not inside the live agent loop

The PII-masking question is architecturally simpler and should move first. req2qa already has a narrow precedent for exactly this concern: `execute_engine.py`'s `_snapshot_elements` masks a fixed `CRITICAL_FIELD_KEYWORDS` list of sensitive DOM field names (ssn, tfn, password, salary) before values reach the model or logs — but this is a field-name blocklist, and free-form requirement text passed into `qa_engine.py`'s prompt templates has no equivalent protection today, going verbatim (up to 120,000 characters depending on call site) straight to Claude via Bedrock. The convergent industry pattern for this exact problem — local detection, placeholder/token substitution, forward only sanitized text to the LLM — appears across every source reviewed (LogRocket, Wavect, philterd.ai, pii-guard, Gravitee), and Presidio is the purpose-built, already-implemented option: it runs fully offline as a Python package, layers regex-based recognizers for structured PII (emails, SSNs, credit cards) with a lightweight spaCy NER pass for names/locations/organizations, and its maintainers report best-case latency under **10ms per 1,000 tokens** with the smaller `en_core_web_sm` model ([Presidio FAQ](https://github.com/microsoft/presidio/blob/main/docs/faq.md); [Presidio latency discussion #1097](https://github.com/microsoft/presidio/discussions/1097)). Against req2qa's own bottleneck — multi-second Bedrock calls and multi-minute agent runs — a tens-of-milliseconds masking pass is not going to become the new critical path.

Two risks specifically shape how narrow the first slice must be. First, **over-masking corrupts business logic, not just privacy**: requirement documents routinely contain illustrative example data that looks like real PII but isn't ("reject if email domain is not @clientcorp.com"), and a comparable local-redaction project (pii-guard) names this exact failure mode, mitigating it with dedicated negative-test fixtures rather than tuning masking to be more aggressive ([pii-guard README](https://github.com/zyphr-labs/pii-guard)). req2qa's `qa_engine.py` prompts also explicitly ask Claude to trace requirement text to test-case IDs and preserve cross-references, so any masking implementation must assign **identical tokens to repeated occurrences of the same entity** within a document — not a fresh token per occurrence — to avoid breaking the structural coherence the prompts depend on; this "scrub-and-rehydrate" pattern with indexed, duplicate-aware tokens (`{{TEST_USER_EMAIL_1}}`) is the standard shape found across every source, though no controlled study was found actually measuring whether token substitution degrades LLM task accuracy — the evidence here is convergent practitioner consensus, not a rigorous experiment. Second, and this is the internal review's own addition rather than something in the sources: **live page-snapshot text must be explicitly excluded from this first slice**, because masking a real success or validation message before the LLM evaluates it risks turning a genuine PASS into a false BLOCKED verdict — a correctness risk with no analog on the requirement-text side, where the text is a static input document rather than a live signal the model is grading. Snapshot-text masking is real future work but belongs in a separate, more latency-sensitive slice that runs inside the agent loop rather than once per document.

The reviewer's recommended smallest-safe-first-step follows directly: **scrub only requirement-text inputs at test-case-generation time**, at the five identified `qa_engine.py` call sites (`run_qa_analysis`, `run_qa_analysis_custom`, `structure_existing_test_cases`, `match_requirements_to_test_cases`, `analyze_requirements_impact`), via a single shared `sanitize(text) -> (masked_text, entity_map)` helper called once per document. Critically, this must **fail open on any masking error** — if Presidio throws, the pipeline should fall back to sending the original text rather than blocking test generation, since a masking bug should degrade privacy protection, not break the product's core function. Before enabling by default, the team should build a small internal fixture set of real req2qa requirement docs containing known "looks-like-PII-but-is-example-data" cases and tune Presidio's confidence thresholds against it, mirroring the negative-test-fixture practice found in comparable tools.

## Conclusion

The two initiatives don't compete for the same engineering budget in the way they might first appear to: masking is a same-week, low-risk addition that closes a real gap (requirement text has zero protection today, versus the DOM field-name blocklist already covering live snapshots), while genuine execution isolation is gated by two specific, named pieces of tech debt — the rate gate and the cancel-event — that have to be redesigned as shared infrastructure before container-per-test can be attempted at all, regardless of which compute platform is chosen. The most useful reframing from this research is that "isolation" and "containerization" are not synonyms for req2qa: the sandbox-only container with AI calls proxied through the existing gate delivers most of the practical value (credential and artifact hygiene between concurrent runs) that motivated the container-per-test idea in the first place, without inheriting any of the four-part migration cost that full out-of-process execution would require. Recommended sequencing is therefore: ship requirement-text masking now (fail-open, snapshot text untouched), build the sandbox-only container as the next infrastructure step, and treat full container-per-test execution — with its distributed rate limiter and distributed cancellation — as a distinct, separately-scoped project to revisit only if isolation requirements outgrow what the sandbox-only design provides.
